## 3. Требования

### 3.1. Функциональные требования (FR)

| ID | Требование |
| :--- | :--- |
| **FR-01** | Система должна поддерживать регистрацию по email и паролю с обязательной валидацией формата email и соответствия пароля политике сложности (минимум 8 символов, заглавные буквы, цифры). |
| **FR-02** | Система должна проверять уникальность email при регистрации и возвращать ошибку `409 Conflict`, если email уже зарегистрирован. |
| **FR-03** | Система должна отправлять на указанный email письмо с одноразовой ссылкой подтверждения (токен действителен 24 часа). |
| **FR-04** | Система должна поддерживать вход по email и паролю с созданием пользовательской сессии (выдача короткоживущего Access Token и Refresh Token). |
| **FR-05** | Система должна поддерживать вход через Google с использованием OIDC Authorization Code Flow с PKCE, не передавая пароль пользователя на Backend. |
| **FR-06** | Система должна поддерживать вход через Apple ID с использованием OIDC, с проверкой подписи токена, issuer, audience и срока действия. |
| **FR-07** | Система должна поддерживать восстановление пароля через одноразовую ссылку на email без раскрытия факта существования email в системе. |

---

### 3.2. Нефункциональные требования (NFR)

| ID | Требование |
| :--- | :--- |
| **NFR-01** | Пароли должны храниться в виде стойких хешей с использованием Argon2id или bcrypt с уникальной солью. |
| **NFR-02** | Передача данных должна выполняться по HTTPS с использованием TLS 1.2+. |
| **NFR-03** | Система должна обеспечивать защиту от перебора паролей (rate limiting), ограничение частоты запросов и безопасное управление сессиями (отзыв Refresh Token при смене пароля). |

## 4. Acceptance Criteria для User Story

### User Story
> **Как** новый пользователь интернет-магазина, **я хочу** зарегистрироваться по email и паролю, **чтобы** получить доступ к личному кабинету и оформлению заказов.

### Acceptance Criteria (Given / When / Then)

| Сценарий | Given (Дано) | When (Когда) | Then (Тогда) |
| :--- | :--- | :--- | :--- |
| **Успешная регистрация** | Email свободен, пароль соответствует требованиям | Пользователь отправляет форму регистрации | Создаётся учётная запись со статусом `pending`, отправляется письмо подтверждения, приложение показывает экран «Проверьте почту» |
| **Email уже существует** | Email зарегистрирован | Пользователь отправляет форму | Система возвращает `409 Conflict`, приложение показывает ошибку и предлагает войти или восстановить пароль |
| **Слабый пароль** | Пароль не соответствует политике безопасности | Пользователь отправляет форму | Регистрация не выполняется, отображаются требования к паролю |
| **Подтверждение email** | Пользователь получил письмо с действующей ссылкой | Переходит по ссылке | Email подтверждается, статус учётной записи меняется на `active` |
| **Ссылка недействительна** | Срок действия ссылки истёк или токен использован | Пользователь открывает ссылку | Система сообщает об ошибке и предлагает запросить новое письмо |
